# Data integrity, ACID and security

The current database works but is not *organised*: ~28 relations are untyped
strings that the database does not enforce, sixteen columns are JSON blobs that
cannot be queried or constrained, stock movement is a free-text log rather than a
ledger, and a unit's history is reconstructed by joining on conventions instead
of keys. None of that is visible until two numbers disagree and nobody can say
which one is right.

This document is the contract that fixes it. Everything else in the plan assumes
it. **Read this before Increment 0**, because most of it is cheaper to build in
than to retrofit.

---

## 1. The one rule

> **The serial number is the subject of this database.**

A unit of stock is a physical device with a serial. Everything else — a SKU, an
order line, a claim, an opname scan — refers to it. It follows that:

- `Unit.serial` is `UNIQUE NOT NULL` and **immutable after creation**.
- Every state change of a unit is an **event row**, never an in-place update
  alone.
- `Unit.status` and `Unit.locationId` are **projections** of that event stream,
  written in the same transaction as the event. They are a cache, and a cache
  that disagrees with its source is a bug we can detect (§6).
- Nothing deletes a unit. Ever. `archivedAt` is the strongest thing available.

Everything in §2–§6 exists to make that rule true under concurrency and failure.

## 2. Invariants, and what enforces each

An invariant that lives only in application code is a wish. Each one below names
the mechanism that actually holds it. "SQL" means a hand-written statement in a
Prisma migration — Prisma's schema language cannot express `CHECK`, partial
unique indexes, or exclusion constraints, so those are added with
`prisma migrate dev --create-only` and then edited.

| # | Invariant | Enforced by |
|---|---|---|
| 1 | A serial exists at most once | `UNIQUE (serial)` on `Unit` |
| 2 | A unit's events are gapless and ordered | `UNIQUE (unitId, seq)` + `seq` assigned inside the txn |
| 3 | A unit is sold at most once at a time | Partial unique: `UNIQUE (unitId) WHERE returnedAt IS NULL` on `OrderItem` |
| 4 | A sold unit cannot be sold again | Status transition table (§4) checked inside the txn under `SELECT … FOR UPDATE` |
| 5 | Order total = Σ line subs − discount + extra | `CHECK` on `Order`, recomputed server-side; the client's total is never trusted |
| 6 | Payments never exceed the order total | `CHECK (amount > 0)` + txn-level assertion on Σ payments |
| 7 | A payment belongs to exactly one parent | `CHECK ((orderId IS NULL) <> (poId IS NULL))` |
| 8 | Money is never negative where it cannot be | `CHECK (amount > 0)`, `CHECK (price >= 0)`, `CHECK (qty > 0)` |
| 9 | A discount cannot be used past its limit | `UPDATE … SET used = used + 1 WHERE used < usageLimit` — the `WHERE` is the lock |
| 10 | Codes (`Order.code`, `PurchaseOrder.code`, …) are unique | `UNIQUE`, generated by a Postgres sequence, not by the app |
| 11 | An opname session counts each serial once | `UNIQUE (sessionId, serial)` on `OpnameScan` |
| 12 | A webhook event is processed once | `UNIQUE (waMessageId)` / `UNIQUE (igCommentId)` + insert-first (§5) |
| 13 | The agent can never overwrite a staff directive | Disjoint column ownership (§7) + test |
| 14 | An audit row is never edited | No `UPDATE`/`DELETE` grant on `AuditLog`, `UnitEvent` for the app role |
| 15 | A unit always has a location | `locationId` `NOT NULL`, FK `ON DELETE RESTRICT` |

> **Test the constraint, not the code path.** Every row above gets an integration
> test that attempts the violation directly against the database and asserts the
> error code. A constraint nobody has seen reject anything is not known to exist.

## 3. Transaction boundaries

Every one of these is a **single** `prisma.$transaction`. Not "mostly" — a
partial checkout is worse than a failed one, because the failed one is obvious.

| Operation | Inside the transaction |
|---|---|
| **Checkout** | Lock each `Unit`; assert `TERSEDIA`; create `Order` + `OrderItem`s; append one `UnitEvent(TERJUAL)` per unit; project `Unit.status`; create `Payment` rows; increment `Discount.used`; create `TradeIn` (+ its incoming `Unit` and `DITERIMA` event); update `Shift` counters |
| **Return / partial return** | Lock units; set `OrderItem.returned*`; append `UnitEvent(RETUR_PELANGGAN)`; project status back to `TERSEDIA`; create `OrderAdjustment`; create reversing `Payment` |
| **Goods arrival** | Lock the PO; create every `Unit` from `PurchaseOrderItemSerial`; append `UnitEvent(DITERIMA)`; allocate PO fees across lines → `Unit.landed`; set `PurchaseOrder.status` |
| **Warehouse transfer** | Lock units; append `UnitEvent(DIPINDAH)` with `fromLocationId`/`toLocationId`; project `Unit.locationId` |
| **Opname posting** | Lock the session; diff scans against `Unit` at that location; append `OPNAME_HILANG` / `OPNAME_DITEMUKAN` events; project statuses; close the session |
| **Warranty resolution** | Lock the unit; append `KLAIM_SELESAI`; project per resolution (`STOK` → `TERSEDIA`, `RETUR` → `RETUR_SUPPLIER`, `REFUND` → `REFUND_KLAIM`); create `Payment` when money moves |
| **Price change** | Update `Sku.price`; insert `PriceLog` — always both, never one |

**Rules.**

- **Isolation.** Default `READ COMMITTED` plus explicit row locks
  (`SELECT … FOR UPDATE`) on every `Unit` a transaction will change. Use
  `SERIALIZABLE` only for opname posting and shift close, which read a whole set
  and decide from it. Serializable transactions **must** be wrapped in a
  retry-on-40001 helper — write that helper once, in `packages/db`.
- **Lock ordering.** Always lock units in ascending `serial` order. Two cashiers
  scanning the same two devices in opposite orders is a real deadlock, and
  ordering is the whole fix.
- **No I/O inside a transaction.** No Graph API call, no Anthropic call, no file
  write. Those happen after commit, driven by an outbox row (§5) — a transaction
  that awaits the network holds locks for as long as the network feels like it.
- **Timeout.** `maxWait: 5s, timeout: 10s`. A checkout that cannot finish in ten
  seconds must fail loudly, not queue behind a lock while a customer waits.
- **Idempotency.** Every mutating endpoint accepts `Idempotency-Key`. The key +
  its response are stored; a repeat returns the stored response instead of acting
  again. The cashier double-clicking Checkout on a slow connection is the single
  most likely way to create a duplicate order.

## 4. The unit state machine

Legal transitions, enforced in `packages/domain/src/unitState.ts` and asserted
inside the checkout/arrival/claim transactions. Anything not in this table is
rejected with a message naming the serial and its current status.

```
                  ┌──────────────► RETUR_SUPPLIER ──► (terminal)
                  │
DITERIMA ──► TERSEDIA ──► DIRESERVASI ──► TERSEDIA
                  │              └────────► TERJUAL
                  ├──► TERJUAL ──► RETUR_PELANGGAN ──► TERSEDIA
                  │        └─────► KLAIM_GARANSI ──┬─► TERSEDIA        (res STOK)
                  │                                ├─► RETUR_SUPPLIER  (res RETUR)
                  │                                └─► REFUND_KLAIM    (terminal)
                  ├──► HILANG ──► TERSEDIA            (found at next opname)
                  └──► KOREKSI_KELUAR ──► (terminal)
```

Two properties matter more than the diagram:

1. **Every arrow is a `UnitEvent` row** carrying `fromStatus`, `toStatus`, who,
   when, and the document that caused it (`orderId`, `poId`, `claimId`,
   `opnameSessionId`).
2. **The event carries `serial` as an immutable copy.** If a `Unit` row is ever
   archived or repaired, the history still reads correctly on its own.

`UnitEvent.seq` is assigned as `MAX(seq)+1` for that unit *inside the
transaction, under the unit's row lock*. That is what makes the ledger gapless
without a global sequence.

## 5. Crossing the boundary: outbox, not fire-and-forget

Sending a WhatsApp reply, posting an IG comment reply, or calling Anthropic are
side effects that must not sit inside a database transaction, and must not be
lost if the process dies after commit.

```
txn: write the row + write an Outbox row   ──commit──►  worker: claim → send → mark
```

- `Outbox(id, kind, payload, status, attempts, nextAttemptAt, lastError, createdAt)`.
- The worker claims with `UPDATE … SET status='SENDING' WHERE id = (SELECT id …
  FOR UPDATE SKIP LOCKED LIMIT 1) RETURNING *` — that one statement is the whole
  concurrency story.
- Retries are exponential with jitter, capped; exhausted rows go to `FAILED` and
  raise an alert, they are never silently dropped.
- Inbound is the mirror image: **persist the raw event first** (`WaRawEvent` /
  `IgRawEvent`), ack Meta, then process. A crash mid-pipeline loses nothing
  because the raw payload is already durable — this is exactly what the current
  webhook already does, and it stays.

## 6. Reconciliation — proving the data is right

Projections drift. Assume it and check for it, on a schedule (nightly, and on
demand from the Monitor app):

| Check | Query shape | On mismatch |
|---|---|---|
| Status projection | `Unit.status` vs the `toStatus` of its highest-`seq` event | Report; never auto-fix silently |
| Location projection | `Unit.locationId` vs latest `toLocationId` | Report |
| Ledger continuity | `seq` sequences with a gap or a duplicate | Alert — this means a bug in the txn |
| Order arithmetic | `Order.total` vs Σ`OrderItem.sub` − discount + extra | Alert |
| Payment coverage | `Order.paidTotal` vs Σ`Payment.amount` where `status=LUNAS` | Alert |
| Orphan units | `Unit` with no `DITERIMA` event | Report (expect only migrated rows) |
| Sold twice | a unit on >1 un-returned `OrderItem` | Alert — invariant 3 should make this impossible |
| Cash | `Shift.expected` vs Σ cash `Payment` in its window | Report on shift close |

Each check is a function in `packages/domain`, called by a script *and* by a
test with a deliberately corrupted fixture, so we know the check itself works.
Results land on a **Integritas Data** panel in the Monitor app, not in a log
nobody reads.

## 7. Column ownership (the structural guarantee)

Two writers, disjoint column sets, on `WaThreadMemory`:

| Writer | May write | May never write |
|---|---|---|
| Webhook summarizer | `summary`, `summaryAt`, `summaryTurns`, `coveredThrough*` | any `directive*` column |
| POS staff (`apps/api`) | `directive`, `directiveAt`, `directiveById` | any `summary*` column |

This is what makes "the agent can never overwrite a staff note" structural
rather than conventional. Keep it, keep the tests that assert it, and apply the
same pattern anywhere else a human and a machine share a row.

## 8. Migrating the existing data

The current database is the source of the mess, so the migration is where the
cleanup actually happens. It is a **one-way ETL into a fresh schema**, not an
`ALTER TABLE` sequence.

**Phase A — profile (read-only, before writing any migration code).**
Run a profiling script that counts, for every loose link: rows whose target does
not exist; duplicate serials; units with no `soldRef` but status `TERJUAL`;
orders whose total ≠ Σ lines; JSON blobs that fail their expected shape. **Do not
guess the volume of bad data — measure it.** The output is a table of
"how many rows will need a decision", and it drives the rest.

**Phase B — decide, per defect class.** Written down, in this repo, before the
loader runs. For each class: fix automatically / quarantine / drop. Silent
coercion is forbidden — a row that cannot be loaded cleanly goes to a
`migration_rejects` table with its reason, and a human looks at the list.

**Phase C — load, in dependency order**, each step idempotent and re-runnable:

```
Location ← distinct Unit.lokasi / Sku.lokasi (deduped, mapped by hand)
Staff, Supplier, Customer, PostalCode
Category → CategoryAttribute/Option/VariantAxis   (from the JSON schemas)
CatalogModel → ModelAxis/Value/Photo → Sku
PurchaseOrder → Item → Serial/Fee/Package/ArrivalPhoto
Unit  (serial is the key; dedupe here or nowhere)
UnitEvent  ← synthesised backfill, see below
Order → OrderItem → Payment/TradeIn/Adjustment
Shipment/Item/Event, Reservation/Item, WarrantyClaim
Discount → DiscountSku, PriceLog, PriceReq
FinSettings/OpexItem, PettyCash/Entry, Shift
Wa*/Ig*/AgentCache
```

**Backfilling `UnitEvent` for historical units.** There is no real history to
recover, so synthesise the minimum truthful skeleton and label it:

- `seq 1` = `DITERIMA` at `Unit.intakeAt`, location from the mapped `lokasi`,
  `staffId` = a reserved `system` staff row, `note = "backfill: migrasi"`.
- `seq 2` = `TERJUAL` at the order's `ts`, when the old `soldRef` resolves to an
  order.
- Nothing else. Do **not** invent transfers or claims.
- Every backfilled row is identifiable (`staffId = system` + the note), so a
  report can always separate real history from reconstructed history.

**Phase D — verify.** Run every check in §6 against the loaded database, plus
row-count and money-total reconciliation against the source. Publish the
before/after numbers. Cutover happens only when the deltas are explained, not
when they are zero — some deltas are the point (deduped serials, dropped
orphans).

Keep the old database **read-only and intact** for at least one quarter. It is
the only appeal court if a number is disputed.

## 9. Security

**Authentication.**
- Argon2id for password hashing (not bcrypt — memory-hard matters more than
  speed here). Cost parameters in config, tuned to ~100 ms on the target host.
- Session token: random 256-bit, stored **hashed** in `StaffSession.tokenHash`;
  the raw value only ever exists in the HttpOnly, `SameSite=Lax`, `Secure` cookie.
  Hashing it means a database leak is not an instant login as every user.
- Rotate the token on privilege change; `revokedAt` gives real "log out
  everywhere". Sessions expire absolutely (e.g. 12 h), not just on idle.
- Rate-limit login per username *and* per IP; every failure writes
  `AuditLog(action = LOGIN_GAGAL)`. Lock-out is progressive delay, not a hard
  lock — a hard lock is a denial-of-service handed to anyone who knows a
  username.

**Authorisation.**
- Checked **server-side, per endpoint**, from `Role` + `canApprove`. The SPA
  hiding a button is a UX affordance, never a control.
- Owner-only: price approval, discounts, staff management, reports, opname
  posting, credential settings, data export.
- Every authorisation denial is logged with the staff id and the target — repeated
  denials are the earliest signal of a compromised or curious account.

**Database.**
- The app connects as a role with `SELECT/INSERT/UPDATE` on business tables and
  **`INSERT` only** on `AuditLog` and `UnitEvent`. No `DELETE`, no `DDL`. Migrations
  run as a different role. This is the difference between "we don't delete audit
  rows" and "we can't".
- Separate read-only role for reporting/monitoring.
- Connection over TLS; credentials from the environment, never in the repo.
- Backups: nightly `pg_dump` + WAL archiving, encrypted at rest, **restore
  rehearsed quarterly**. An unrehearsed backup is a hypothesis.

**Data handling.**
- PII is customer name, phone, address, and WhatsApp/IG identity. It is never put
  in a URL, a query string, a log line, or an analytics event.
- Logs redact by allowlist-of-shape, not blocklist-of-name, where possible; the
  existing `packages/logging/src/redact.ts` rules are the floor, not the ceiling.
- Export endpoints (CSV) are owner-only, rate-limited, and each export writes
  `AuditLog(action = EKSPOR)` with the row count. Bulk exfiltration should leave a
  mark.
- Retention: raw webhook payloads 30 days, HTTP logs 30 days, audit and unit
  events **forever**.

**Application.**
- Every request body validated with Zod before it reaches a query. Prisma
  parameterises, but validation is what stops a well-formed request from writing
  nonsense.
- No raw SQL with interpolation; `$queryRaw` only with tagged-template
  parameters, and only where Prisma genuinely cannot express the query.
- CORS locked to the SPA origin; CSRF defended by `SameSite=Lax` plus an origin
  check on mutations.
- Security headers via helmet: HSTS, `X-Content-Type-Options`, a CSP that
  disallows inline script.
- Uploads (arrival photos, unit-note photos): type and size validated, stored
  outside the web root under generated names, served through an authorised route.
  Never trust the client-supplied filename.
- Dependencies: `pnpm audit` in CI, and CI fails on a high-severity advisory.

- [ ] The Phase A profiling report exists, with real numbers from the current database
